# VrHitchLog

*[English version](README.md)*

Консольная утилита для Windows, которая помогает найти причину **периодических микрофризов в PC VR**: SteamVR, VRChat, Virtual Desktop, Pico Connect, Air Link, Steam Link. Она записывает на одной шкале времени всё, из-за чего картинка может на мгновение замереть:

- каждый кадр компоновщика SteamVR;
- остановки каждого ядра CPU (DPC/ISR, драйверы, прошивка);
- системные счётчики и самые активные процессы;
- **пинг шлема или роутера 50 раз в секунду**.

В итоге видно, откуда фризы: из ПК, из игры или из сети.

> **Что нашлось с её помощью:** фриз в беспроводном VR примерно **каждые 5,2 секунды** из-за службы **`trafficd` на роутере Xiaomi/Redmi**. Если у вас роутер Xiaomi или Redmi и фризы идут с постоянным ритмом ~5 с, сначала прочитайте **[разбор случая](docs/case-xiaomi-trafficd.ru.md)**.

## Что записывается

| Файл | Что внутри | Частота |
|---|---|---|
| `frames.csv` | каждый кадр компоновщика SteamVR: интервал, пропуски, повторы, время CPU/GPU (те же данные, что у fpsVR) | каждый кадр |
| `stalls.csv` | «остановки» ядер: поток-зонд на каждом логическом ядре спит 1 мс; если он проснулся позже 4 мс, ядро было занято драйвером (DPC/ISR), realtime-потоком или прошивкой | по факту |
| `sys.csv` | CPU, DPC и прерывания (всего и худшее ядро), подкачка, память, самый медленный диск | 4 раза/с |
| `disks.csv` | задержка, очередь и скорость каждого диска | 4 раза/с |
| `sys_slow.csv` | загрузка движков GPU (3D, копирование, кодирование видео…), кто больше всех грузит 3D, память GPU, сеть, температура | 1 раз/с |
| `procs.csv` | самые активные процессы: CPU, hard page faults, дисковый ввод-вывод, память | 1 раз/с |
| `events.csv` | найденные фризы с контекстом: совпал ли спайк кадра с остановкой ядер, что было с DPC, диском, памятью, какие процессы были активны | по факту |
| `net.csv` | с `--ping IP`: время отправки и задержка каждого пинга (−1 — потерян) | 50 раз/с |
| `summary.txt` | статистика кадров, остановки по ядрам, фризы ≥60 мс и их период, провалы пинга и сколько фризов с ними совпало | в конце |
| `session.txt` | железо, Windows, BIOS, гипервизор, разрешение таймера, план питания, имена запущенных программ | в начале |

## Сборка

Нужен .NET SDK 8 или новее (ставится вместе с Visual Studio). Запустите **`build.cmd`**, программа появится в папке `out`.

При первой сборке `openvr_api.dll` скачивается с официального GitHub Valve. Если скачать не получилось, возьмите файл вручную (<https://github.com/ValveSoftware/openvr/tree/v2.5.1/bin/win64>) и положите в `third_party\openvr\`.

## Запуск

1. Запустите **`out\run.cmd`** до или после SteamVR, порядок не важен. Программа сама подключится к SteamVR, когда он появится, и переживёт его перезапуск. Сама SteamVR она не запускает.
2. Играйте как обычно. Раз в 5 секунд в окне появляется строка состояния.
3. Остановка: **Q** или **Ctrl+C** в окне программы. Не закрывайте окно крестиком, иначе не соберутся итог и архив.
4. Данные сессии лежат в `%LOCALAPPDATA%\VrHitchLog\session-ДАТА-ВРЕМЯ\`, рядом — `.zip` с ними же.

**`out\run-wpr.cmd`** делает то же самое и вдобавок пишет трассы WPR (попросит права администратора). Windows Performance Recorder держит последнюю минуту событий ядра в памяти и при сильном фризе сохраняет её в `.etl` (до 3 трасс за сеанс). Файлы `.etl` открываются в Windows Performance Analyzer.

### Параметры

```
--minutes N     остановиться через N минут
--ping IP       пинговать этот адрес 50 раз/с (net.csv) и сопоставить провалы сети с фризами
--no-probe      без зондов на ядрах (например, для чисто сетевого теста)
--wpr           трассы WPR при сильных остановках (нужен администратор)
--wpr-ms N      порог остановки ядер для трассы, мс (40)
--wpr-max N     максимум трасс за сеанс (3)
--event-ms N    что считать событием, мс (20)
--gap-ms N      писать в stalls.csv остановки ядра от N мс (4)
--cores 0,2,4   зонды только на этих ядрах
--out DIR       куда писать
```

Примеры (из папки `out`):
```
:: IP шлема, во время игры
run.cmd --ping 192.168.1.50

:: сам роутер, ПК подключён кабелем
run.cmd --no-probe --ping 192.168.1.1 --minutes 3 --out D:\vrlog\router
```
Можно запускать два экземпляра одновременно, например один пингует шлем, другой роутер. Дайте им разные папки `--out`.

## Как читать

- **Спайк кадра совпал с остановкой почти всех ядер.** Встала вся машина: драйвер, прошивка/BIOS (SMI), гипервизор.
- **Спайк кадра совпал с остановкой одного-двух ядер.** Конкретный драйвер держит DPC/ISR (часто ядро 0). Трасса WPR покажет, какой именно.
- **Спайк кадра без остановок ядер, пинг чистый.** Проблема выше: игра (загрузка аватаров, сборка мусора), подкачка, диск, GPU или сам SteamVR.
- **Спайк кадра совпал с провалом пинга.** Виновата сеть. В `net.csv` провал обычно выглядит как «лесенка» убывающей задержки, например `176, 156, 136 … 17` мс: пакеты стояли в очереди и вышли вместе.
- **Ровный интервал между событиями** (каждые 5,2 с, 30 с, 60 с…). Почти всегда что-то опрашивает по таймеру: программа, драйвер или **роутер**.

Как отличить роутер от шлема:
1. Одновременно со шлемом пингуйте второе Wi-Fi-устройство (телефон с включённым экраном). Если оба провисают в одной фазе, виноват роутер.
2. Пингуйте сам роутер с ПК, подключённого кабелем. Если провисает и он, роутер зависает целиком.

Ещё один признак, что драйверу стриминга не хватает сети: в `Steam\logs\vrcompositor.txt` с ровным интервалом повторяется строка `WaitForAcquire timed out (FAILED); rendering the next frame before the driver took the sync texture`.

## Приватность

Пишутся только числа и имена процессов: без путей, командных строк и содержимого окон. Всё же перед публикацией сессии просмотрите `session.txt`: в нём ваше железо и имена запущенных программ. Пингуемый IP (локальный адрес) есть в `session.txt`, `log.txt` и `summary.txt`.
