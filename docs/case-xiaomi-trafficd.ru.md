# Разбор случая: фризы в VR каждые 5,2 секунды из-за роутера Xiaomi / Redmi (`trafficd`)

*[English version](case-xiaomi-trafficd.md)*

**Коротко.** В беспроводном PC VR картинка замирала на 100–180 мс почти ровно раз в **5,18–5,20 секунды**. ПК, SteamVR, игра и шлем были ни при чём. Причина — заводская прошивка роутера **Redmi Router AX6000** (MiWiFi, версия 1.0.67): служба Xiaomi **`/usr/sbin/trafficd`** раз в ~5,2 с блокирует роутер примерно на 170 мс. После её остановки фризы пропали полностью.

Если у вас роутер Xiaomi или Redmi на заводской прошивке и фризы идут с постоянным ритмом около 5 секунд, скорее всего, это ваш случай.

---

## Конфигурация

- Шлем: PICO 4 Pro, стриминг по Wi-Fi 6 (5 ГГц, связь 1200 Мбит/с) через **Virtual Desktop**. Те же фризы были раньше и с **Pico Connect**.
- Трекинг всего тела: базовые станции Lighthouse, трекеры Vive/Tundra, контроллеры Index.
- ПК: Ryzen 7 9700X, RTX 5080, Windows 10 22H2, подключён к роутеру **кабелем**.
- Роутер: Redmi Router AX6000 (RB06), заводская прошивка 1.0.67. Это последняя прошивка Xiaomi для этой модели, январь 2023.

## Симптом

- Короткое замирание («микрофриз») раз в несколько секунд, и в VRChat, и в пустом SteamVR.
- В fpsVR — одинокий спайк времени кадра, при этом замирает и сам SteamVR.
- В оверлее производительности Virtual Desktop сначала желтеет **Encoding**, потом **Networking**.

## Что *не* помогло

Это стандартные советы, и на них уходит много времени:

- Отключение MPO, план питания, файл подкачки, обновление BIOS и чипсета.
- Перенос Steam/SteamVR с HDD на SSD.
- Отключение дополнительных драйверов и оверлеев SteamVR.
- Смена канала 5 ГГц на роутере (Auto → 36) и ширины (160 → 80 МГц). Настройка разумная, но причина была не в ней.
- Отключение MU-MIMO. Шлем стал реже попадать под провал, но сам роутер продолжал зависать.

## Как нашли (с VrHitchLog)

1. **Тайминги кадров.** Компоновщик SteamVR ждал новую позу шлема каждые **5,19 с** (±3%), даже без запущенной игры.
2. **ПК исключён.** Зонды на каждом ядре **не** показали в эти моменты ни остановок CPU, ни DPC, ни прерываний.
3. **Лог SteamVR.** В `vrcompositor.txt` тот же ритм:
   ```
   WaitForAcquire timed out (FAILED); rendering the next frame before the driver took the sync texture
   ```
   Интервалы между такими строками: 5,22, 5,18, 5,17, 5,19 с… Драйвер стриминга (Virtual Desktop) не успевал забрать кадр.
4. **Пинг шлема 50 раз в секунду** (`--ping <IP шлема>`). Каждые 5,18 с шлем замолкал на ~180 мс. Потом все задержанные ответы приходили разом, поэтому задержка убывает «лесенкой» с шагом 20 мс (интервал между пингами):
   ```
   176, 156, 136, 116, 96, 76, 56, 36, 17 мс ... и снова ~3 мс
   ```
   Такой рисунок значит, что пакеты где-то **стояли в очереди** и вышли вместе, а не потерялись.
5. **Телефон в той же сети 5 ГГц** провисал точно так же и **в той же фазе**, что и шлем: сдвиг 0,38 с не менялся все 3 минуты. Два независимых устройства не могут случайно совпасть по ритму, значит, «часы» были в роутере.
6. **Пинг самого роутера по кабелю** (`--ping 192.168.31.1`, адрес роутеров Xiaomi по умолчанию). Он тоже провисал каждые 5,18 с, до 177 мс. Wi-Fi на этом пути не участвует, значит, зависал сам роутер.
7. **SSH на роутер и `top -d 1`.** Примерно в одном кадре из пяти `trafficd` занимал ~4% CPU. В `top` из busybox проценты считаются от всех 4 ядер, то есть 4% — это ~170 мс одного ядра. Совпадает с длиной провала.
8. **Доказательство.** `/etc/init.d/trafficd stop`. Пинг роутера: было 24 всплеска ≥50 мс (до 177 мс) за 2 минуты, стало **0 всплесков, максимум 11 мс**. Другое Wi-Fi-устройство: было 35 всплесков и 19 потерь, стал 1 случайный всплеск. Фризы в VR исчезли.

`trafficd` — служба Xiaomi, которая собирает статистику трафика по устройствам для веб-интерфейса и приложения Mi Wi-Fi. Без неё пропадает только эта статистика.

## Решение

Доступ к роутеру: в заводской прошивке SSH нет. **[XMiR-Patcher](https://github.com/openwrt-xiaomi/xmir-patcher)** (открытый проект, под Windows запускается через `run.bat`) умеет включать SSH на вашем роутере. Пункт `2` открыл SSH на прошивке 1.0.67 без отката версии, пункт `6` сделал SSH постоянным. XMiR-Patcher ставит пароль root `root`, поэтому **потом смените его командой `passwd`**. Пункт `4` делает полный бэкап флеша — сделайте его до любых изменений.

Клиенту OpenSSH в Windows нужно разрешить старый тип ключа:
```
ssh -o hostkeyalgorithms=+ssh-rsa -o pubkeyacceptedalgorithms=+ssh-rsa root@192.168.31.1
```
Если ssh пишет, что ключ хоста изменился (так бывает после каждого нового запуска эксплойта), выполните `ssh-keygen -R 192.168.31.1`.

### Сначала проверить (временно)

```
/etc/init.d/trafficd stop
ps | grep trafficd
```
Действует до следующей перезагрузки роутера. Проверьте VR сразу.

### Чтобы переживало перезагрузку

`/etc/init.d/trafficd disable` на этой прошивке **не хватает**. При каждой загрузке прошивка заново создаёт ссылку `/etc/rc.d/S77trafficd` (у неё дата 1970 года — её создают до синхронизации часов). После незаметной перезагрузки роутера фризы вернулись через неделю.

Перезагрузку переживает постоянный раздел `/data` плюс скрипт-«include» фаервола, который прошивка запускает при каждой загрузке:

```sh
echo '#!/bin/sh' > /data/no_trafficd.sh
echo '(sleep 90; /etc/init.d/trafficd stop; /etc/init.d/trafficd disable) >/dev/null 2>&1 &' >> /data/no_trafficd.sh
chmod +x /data/no_trafficd.sh

uci set firewall.notrafficd=include
uci set firewall.notrafficd.type='script'
uci set firewall.notrafficd.path='/data/no_trafficd.sh'
uci set firewall.notrafficd.enabled='1'
uci commit firewall
```
Скрипт ждёт 90 с, чтобы сработать после того, как прошивка запустит все свои службы. Проверка после `reboot` (подождите хотя бы 2 минуты):
```
uptime
ps | grep trafficd                 # должна остаться только строка самого grep
uci show firewall | grep notrafficd
```

**Откат:**
```
uci delete firewall.notrafficd; uci commit firewall
rm /data/no_trafficd.sh
/etc/init.d/trafficd enable; /etc/init.d/trafficd start
```

### Другие варианты

- **OpenWrt.** Redmi AX6000 [хорошо поддерживается](https://openwrt.org/toh/xiaomi/redmi_ax6000), и фоновых служб Xiaomi там нет. Образы «stock layout» ставятся через XMiR-Patcher (пункт `7`) без замены загрузчика. В этом случае не понадобилось, но это самый чистый вариант на будущее.
- **Отдельная точка доступа только для шлема**, подключённая кабелем к ПК. Тогда домашний роутер вообще не влияет на VR.

## Как проверить у себя

Нужен ПК, подключённый к роутеру **кабелем**, и [VrHitchLog](../README.ru.md) или любая программа, которая пингует 50 раз в секунду.

1. Пингуйте сам роутер 2–3 минуты:
   ```
   VrHitchLog.exe --no-probe --ping 192.168.31.1 --minutes 3
   ```
   Всплески 100+ мс с **медианным интервалом ~5,2 с** в `summary.txt` значат, что роутер зависает.
2. Пингуйте шлем (`--ping <IP шлема>`), пока он подключён и идёт стрим. Ищите в `net.csv` «лесенку» убывающей задержки.
3. Короткий тест в простое может оказаться чистым, даже когда `trafficd` работает. В этом случае провалы были сильнее всего, когда шлем был подключён и шёл стрим. Надёжная проверка — `ps | grep trafficd` на роутере.

Обычный `ping -t` в Windows отправляет один пинг в секунду и ловит провал в 180 мс лишь изредка. Ритм становится виден только при частом пинге.
